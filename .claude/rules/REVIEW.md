# Code Review

Критерии ревью кода в проекте. Цель — поймать до мёржа всё, что вредит
**читаемости**, **поддерживаемости** и **отслеживаемости багов**. Стандарт того,
*как писать*, задан в `CODE_STYLE.md`; здесь — *что отмечать* и *насколько серьёзно*.

---

## Область ревью

- Анализируй **все изменения в текущей ветке** (commits + staged + unstaged).
- База для сравнения — **`dev`** (если ревью идёт под другую базу — сравнивай с ней).
- Не ревьюй код вне изменений. Если проблема вне diff, но **вызвана** изменениями —
  пометь её как **смежную** и опиши.
- В рамках ревью **не делай `commit` и не создавай PR** без явного запроса.

---

## Стек проекта

- Next.js 15.3 (App Router, Turbopack в dev), React 19, TypeScript 5 (`strict`).
- Слои (**не FSD**): `app` (роуты + `api`), `views`, `ui`, `services` (server-only),
  `actions`, `lib`, `hooks`, `contexts`, `db/schema` (Drizzle), `routes`.
- Данные: Drizzle ORM 0.45 + Neon Postgres (`@neondatabase/serverless`), PGlite в тестах.
- Auth: argon2, session, OTP / magic-link, Telegram-verify; RBAC через `UserRole` + `useAccess`.
  Внешний API на api-ключах (`app/api/external/*`).
- Стили: Tailwind 4, токены в `globals.css`, `clsx`. Тесты: Vitest (`*.test.ts` рядом).

## Как пользоваться приоритетами

- **Critical** — блокирует мёрж: баги, дыры в доступе/тенанте, утечки секретов,
  сломанные контракты. Чинить до мёржа.
- **Middle** — чинить в этом PR либо завести явный follow-up: слабая типизация,
  DRY/KISS, нет теста/валидации, нет revalidate.
- **Low** — улучшение: нейминг, порядок импортов, форматирование, мелкая неоптимальность.

Сначала отрабатывай Critical, потом Middle, потом Low.

---

## Critical

**Корректность и устойчивость**

- баги, гонки, утечки памяти/подписок; необработанный `await`/промис.
- эффект без снятия подписки в cleanup; `useEffect`/`useMemo`/`useCallback` с неверными
  зависимостями, дающими гонку или устаревшее замыкание.

**Доступ и мультитенантность**

- сервис/экшен читает или меняет данные **без** `getCurrentUser()` и `checkBusinessAccess()`.
- запрос к БД **без фильтра по `businessId`** — утечка данных между бизнесами (проверки доступа
  *недостаточно*, фильтр обязателен).
- операция уровня OWNER/MANAGER **без проверки роли на сервере** (`getBusinessRole` +
  `isOwnerOrManager`) — участник дёрнет экшен в обход UI-гейтинга.

**Внешний API (`app/api/external/*`)**

- route без `requireAuth(req, scope)` или с неверным scope.
- `businessId` берётся **из тела запроса**, а не из `auth.ctx`.
- ответ в обход `apiOk`/`apiError` (теряется `x-request-id` и единый формат).
- запись без идемпотентности по `idempotency_key` (риск дублей).

**Секреты и server-only**

- секреты / ключи / хеши паролей / токены в ответе API, в логах или в клиентском бандле.
- `whitelist` / admin-id / ключ в `NEXT_PUBLIC_*` (всё это уходит в клиент).
- серверный модуль без `import 'server-only'`, способный утечь в клиент; импорт `services`/`lib`
  напрямую в клиентский компонент (минуя `actions`/API).
- небезопасная работа с токенами (otp, magic-link, invite, email-token): нет проверки
  срока действия или одноразовости.

**Контракты и ошибки (отслеживаемость)**

- нарушение публичного контракта (`ServiceResult`/`ActionResult`, `*Input`-типы) без правки
  всех мест использования; параллельная форма ответа (`success`/`message`) вместо `{ ok }`.
- `throw` для **ожидаемой** ошибки вместо `ServiceResult`/`ActionResult`.
- **проглоченная ошибка**: пустой `catch {}`, либо `catch`, который не логирует и не пробрасывает.
- ожидаемая ошибка без стабильного машинного `code` (или код-синоним вне каталога) — теряется
  точка трассировки и завязка HTTP-статусов/тестов.

**Данные**

- изменение `db/schema/*` без сгенерированной миграции (`npm run db:generate`).

**React**

- неверные/нестабильные `key` в списках (индекс вместо доменного id).

**Моки**

- мок без паттерна `USE_*_MOCK` или без обоснования невозможности на бэке (см. `MOCKS.md`).

## Middle

- слабая типизация / `any`; ручное дублирование типов вместо вывода из `db/schema`
  (`$inferSelect`/`$inferInsert`); лишние `as`.
- нарушение DRY / KISS (пример: локальная копия `checkBusinessAccess` вместо `services/_access.ts`;
  переобъявление `UNAUTHORIZED`/`FORBIDDEN` вместо общего источника).
- смешение бизнес-логики и UI (логику и загрузку данных не вынесли в хук/экшен).
- server action **без `revalidatePath`** после мутации.
- отсутствие валидации входа: нет `trim`, нет проверки на пустоту, нет clamp пагинации
  (`MAX_PER_PAGE`).
- новая серверная логика **без теста**; нет теста на ветку ошибки (доступ/валидация/конфликт).
- неоднородные сообщения об ошибке: пользователю утекает технический текст/стек, либо
  лог без тега/контекста (нечем грепать инцидент).
- сложночитаемый код: переусложнённый JSX, компонент сильно за ~250–300 строк без декомпозиции.
- unrelated diff в PR (рефакторинг, lint, файлы не по задаче) — выноси отдельным PR.

---

## Low

- нейминг (переменные, файлы, компоненты, обработчики `handleX`, boolean `is/has/can`).
- порядок и группировка импортов; алиас `@/*` вместо относительных путей.
- форматирование / стилистика кода.
- неоптимальная, но корректная реализация (тяжёлый расчёт в рендере вместо `useMemo`).
- хардкод пути вместо `routes/routes.ts`.
- хардкод цвета/hex вместо токена из `globals.css`; условные классы без `clsx`.

## Тематические чек-листы

Проходи по блокам для серверной логики, доступа к данным, внешнего API и навигации.

### Слои и границы

- новый код в правильном слое (`services`/`actions`/`ui`/`views`/`lib`), не свален в один файл. *(Middle)*
- `ui/*` не знает домена; доменная логика — в `services/*`. *(Middle)*
- `services/*` и доступ к БД помечены `server-only` и не импортируются в клиент. *(Critical)*

### Доступ к данным и тенант

- последовательность `getCurrentUser → checkBusinessAccess → фильтр по businessId` соблюдена. *(Critical)*
- проверки доступа — общие (`services/_access.ts`), а не копии в каждом файле. *(Middle)*
- роль на сервере дублирует UI-гейтинг для чувствительных операций. *(Critical)*

### Внешний API

- scope берётся из api-key (`requireAuth`), контекст бизнеса — из `auth.ctx`. *(Critical)*
- ответы через `apiOk`/`apiError`; `x-request-id` пробрасывается. *(Critical / Middle)*

### Ошибки и отслеживаемость

- ожидаемое → `ServiceResult`/`ActionResult` с `code` из каталога; неожиданное → лог с тегом
  `'<scope>.<fn> failed:'` + контекст без секретов. *(Critical / Middle)*
- нет проглоченных ошибок; фоновые эффекты (email/telegram) логируются и не роняют поток. *(Critical / Middle)*
- на значимые ветки ошибок есть тесты. *(Middle)*

### Env и доступ

- `NEXT_PUBLIC_*` — только осознанно клиентские несекретные значения; ключи/токены/списки id —
  server-only env + проверка на сервере. *(Critical)*
- клиент узнаёт о доступе через API/контекст (роль из `useAccess`), а не сравнением id с массивом
  из бандла. *(Critical)*

### Данные и миграции

- enum как const-кортеж + `$type<>()`; типы выведены из схемы. *(Middle / Low)*
- схема менялась → миграция сгенерирована и в PR. *(Critical)*

### Навигация и единый источник

- пути из `routes/routes.ts`, не хардкод строкой в нескольких местах. *(Middle / Low)*

### Scope PR

- изменения вне задачи — отдельный PR. *(Middle)*

## Формат ответа

Для каждой найденной проблемы:

- **Уровень:** Critical / Middle / Low
- **Где:** файл и участок diff (`path:line`)
- **Проблема:** что не так
- **Почему это плохо:** последствие (баг, утечка, рост стоимости поддержки, потеря трассировки)
- **Как исправить:** конкретное действие или пример кода

Если критичных проблем нет — скажи это явно и перечисли только Middle/Low.
Отмечай отклонения **только в рамках изменённого diff**, опираясь на `CODE_STYLE.md`.
