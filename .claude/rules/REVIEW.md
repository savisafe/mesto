# Code Review

## Область ревью

- Анализируй **все изменения в текущей ветке** (commits + staged + unstaged).
- Базовая ветка для сравнения — `dev` (если ревью идёт под другую базу — сравнивай с ней).
- Не ревьюй код вне изменений. Если проблема вне diff, но вызвана изменениями — пометь: смежная.

---

## Стек проекта

- Next.js 15.3 (App Router, Turbopack в dev), React 19, TypeScript 5.
- Слоистая структура (**не FSD**): `app` (роуты + `api`), `views`, `ui`, `services` (server-only), `actions`, `lib`, `hooks`, `contexts`, `db/schema` (Drizzle), `routes`.
- Данные: Drizzle ORM 0.45 + Neon Postgres (`@neondatabase/serverless`), pglite для тестов.
- Auth: argon2, session, OTP / magic-link; RBAC через `UserRole` + `useAccess`. Внешний API на api-keys (`app/api/external/*`).
- Стили: Tailwind 4, токены в `globals.css`, `clsx`.
- Тесты: Vitest (`*.test.ts` рядом с кодом).

## Приоритеты

**Critical:**

- баги, гонки, утечки
- **доступ:** сервис/экшен читает или меняет данные без `getCurrentUser()` и `checkBusinessAccess()`
- **мультитенантность:** запрос к БД без фильтра по `businessId` (утечка данных между бизнесами)
- **внешний API:** route в `app/api/external/*` без `requireAuth(req, scope)` или с неверным scope; `businessId` берётся из тела запроса, а не из `auth.ctx`
- секреты / ключи / хеши паролей / токены в ответе API, логах или клиентском бандле
- серверный модуль без `import 'server-only'`, утекающий в клиент
- небезопасная работа с токенами (otp, magic-link, invite, email-token): нет проверки срока действия или одноразовости
- нарушение публичного контракта модулей (`ServiceResult`/`ActionResult`, `*Input`-типы)
- неправильные `key` в списках
- вызовы функций в JSX без необходимости; сложная логика в JSX
- `throw` для ожидаемой ошибки вместо `ServiceResult`/`ActionResult`
- изменение `db/schema/*` без сгенерированной миграции
- мок без паттерна `USE_*_MOCK` или без обоснования невозможности на бэке (см. `MOCKS.md`)
- `whitelist` / admin ID / секреты в `NEXT_PUBLIC_*` (попадают в клиентский бандл)

**Middle:**

- слабая типизация / `any`; ручное дублирование типов вместо вывода из `db/schema`
- нарушение DRY / KISS (пример: локальная копия `checkBusinessAccess` вместо `services/_access.ts`)
- смешение логики и UI (нет хуков)
- server action без `revalidatePath` после мутации
- отсутствие валидации входа (нет `trim`, нет clamp пагинации)
- новая серверная логика без теста
- сложночитаемый код
- unrelated diff в PR (рефакторинг, lint, файлы не по задаче)

**Low:**

- нейминг (переменные, файлы, компоненты)
- порядок импортов
- форматирование / стилистика кода
- неоптимальная, но корректная реализация
- хардкод пути вместо `routes/routes.ts`
- хардкод цвета вместо токена из `globals.css`

## Базовые правила

- Используй единые правила из `CODE_STYLE.md`; отмечай отклонения только в рамках изменённого diff.
- В рамках ревью не выполняй `commit` и не создавай pull request без явного запроса пользователя.

## Архитектура и инфраструктура

Проверять для серверной логики, доступа к данным, внешнего API, навигации.

### Слои и границы

- **Middle:** новый код лежит в правильном слое (`services`/`actions`/`ui`/`views`/`lib`), а не свален в один файл.
- `ui/*` не знает домена; доменная логика — в `services/*`.
- **Critical:** `services/*` и доступ к БД помечены `import 'server-only'` и не импортируются в клиентские компоненты.

### Доступ к данным и тенант

- **Critical:** каждый сервис проверяет пользователя (`getCurrentUser`) и доступ к бизнесу (`checkBusinessAccess`), затем фильтрует запрос по `businessId`.
- Проверки доступа — общие (`services/_access.ts`), а не копии в каждом файле.
- Внешний API: scope берётся из api-key (`requireAuth`), контекст бизнеса — из `auth.ctx`.

### Env и доступ

- **Critical:** `NEXT_PUBLIC_*` — только осознанно клиентские значения. Ключи, токены, списки ID — server-only env + проверка на сервере.
- Клиент узнаёт о доступе через API / контекст (роль из `useAccess`), а не сравнивая ID с массивом из бандла.
- `NEXT_PUBLIC_` для «секретов» не считается server-only: значение всё равно уходит в клиент.

### Навигация и единый источник

- **Middle:** пути берутся из `routes/routes.ts`; новый маршрут не хардкодится строкой в нескольких местах.

### Scope PR

- **Middle:** изменения вне задачи — отдельный PR.
